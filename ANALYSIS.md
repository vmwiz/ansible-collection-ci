# Analysis: how the `ansible-collections` collections build their CI

*Survey done on 20/10/2026 (repositories cloned with `--depth 1` on their default branch, commits from 23/06 to 20/10/2026). Sources checked in the code of ansible-core 2.21.5, antsibull-nox 1.9.3, tox-ansible 26.10.0, galaxy-importer 0.4.44.*

## 1. Summary

1. **The test engine is still `ansible-test` everywhere** (sanity, units, integration), almost always with `--docker`. The image is `default` (`quay.io/ansible/default-test-container`) or a distribution image (`ubuntu2404`, `fedora43`, `alpine323`...). All the Python versions shipped in the image are tested at once.
2. **Matrix = ansible-core series × (Python versions | images)**: `stable-2.19` ... `stable-2.21`, plus `milestone`/`devel`. There is one `tests/sanity/ignore-2.X.txt` file per series.
3. **Three "families" of shared tooling** have replaced hand-written workflows:

   | Family | Used by | Mechanism |
   |---|---|---|
   | **antsibull-nox** (community, Felix Fontein) | community.general, .docker, .crypto, .dns, .routeros, .sops, (.postgresql, .vmware, ansible.mysql for the "extra checks") | `noxfile.py` + `antsibull-nox.toml`; reusable workflows `reusable-nox-matrix.yml` / `reusable-nox-run.yml`. **Same logic locally, on GHA and on AZP**, through `tests/utils/shippable/nox.sh` |
   | **ansible/ansible-content-actions** + **ansible-network/github_actions** (Red Hat) | cisco.ios, arista.eos, ansible.netcommon, ansible.utils, kubernetes.core, amazon.aws | Reusable workflows (`sanity.yaml`, `unit.yaml`, `ansible_lint.yaml`, `build_import.yaml`, `changelog.yaml`, `release.yaml`), matrix generated by **tox-ansible** (`tox --ansible --gh-matrix`) |
   | **ansible-community/ansible-test-gh-action** | collection_template, amazon.aws (sanity/units), community.vmware, azure, community.grafana, ansible.mysql | Composite action: installs ansible-core and the dependencies, then runs `ansible-test ... --docker` |

4. **Azure Pipelines (AZP) is still widely used** by the big community collections: community.general, .crypto, .docker, .postgresql, .libvirt, .rabbitmq, ansible.posix, ansible.windows. Jobs run in `quay.io/ansible/azure-pipelines-test-container:8.0.0` with the agent's Docker socket. AZP is mostly used for the `--remote` targets (RHEL, FreeBSD, macOS, Windows VMs), paid through the "Ansible Core CI" and **not reachable outside the Red Hat infrastructure**.
5. **"Application" integration tests**: service containers started alongside (docker compose for Vault or Zabbix, GHA `services:` for MySQL/MariaDB) then `--docker-network`, a **kind** cluster (kubernetes.core), a **Cisco CML** lab (network collections), real cloud accounts (amazon.aws through `ansible/ansible-test-auth`, azure).
6. **Quality / publication**: `antsibull-changelog lint` (mandatory fragments in `changelogs/fragments/`), `ansible-lint`, **galaxy-importer** (same validation as Galaxy/Automation Hub), `antsibull-docs` (docs-pr/docs-push), then `ansible-galaxy collection build/publish` on a tag (`release.yaml` → Galaxy + Automation Hub).
7. **Molecule**: **4 of the 23 collections in the table** (≈ 17 %). Two test **roles** on real containerised OSes: community.zabbix (12 scenarios, `driver: default` and custom create/destroy with `privileged` systemd images) and community.grafana (1 scenario, `docker` driver from molecule-plugins). Two use it as an **integration harness without a real device**: cisco.ios (32 `extensions/molecule` scenarios, ansible-native configuration, SSH simulator `cisshgo`) and ansible.scm (6 scenarios run by `pytest-ansible`). community.sops, which also has roles, tests them with `ansible-test integration` targets. No collection uses Molecule **instead of** ansible-test.

## 3. Common patterns (what must be reproduced)

### 3.1 Directory layout required by ansible-test
`ansible-test` must run from `.../ansible_collections/<namespace>/<name>/`. Each CI handles this its own way:
* `checkoutPath: ansible_collections/community/general` (AZP);
* `actions/checkout` with `path: ansible_collections/${NAMESPACE}/${COLLECTION_NAME}` (hashi_vault, zabbix);
* `rsync` to `{envtmpdir}/.../ansible_collections/amazon/aws` (amazon.aws tox).

Collection dependencies are installed **in the same `ansible_collections` root**. ansible-test then ships them into the container (checked in `ansible_test/_internal/payload.py`: *"include files from each collection in the same collection root"*). They come from `ansible-galaxy collection install`, from a `git clone` (ansible.posix: *"we're installing with git to work around Galaxy being a huge PITA"*), or from the git `collection_sources` of antsibull-nox.

### 3.2 ansible-test invocations actually used
```bash
ansible-test sanity --color -v --junit --docker [--base-branch ...] [--allow-disabled]    # ansible.posix
ansible-test units --color -v --docker default [--coverage] [--changed]                  # libvirt, rabbitmq
ansible-test integration --color -v --retry-on-error <target> --docker <image>           # posix linux.sh
ansible-test integration -v --retry-on-error --continue-on-error --python X --docker default \
             --docker-network hashi_vault_default                                        # hashi_vault
ansible-test coverage xml -v --requirements --group-by command --group-by version        # rabbitmq/zabbix
ansible-test <cmd> --prime-containers                                                    # hashi_vault (pre-pull)
```
Control conventions: `ci_complete` / `ci_coverage` in the commit message, `--changed` for PRs (change detection), `--coverage-check` by default, `--coverage` at night.

### 3.3 Matrices observed (October 2026)
* ansible-core series: **2.19, 2.20, 2.21** in every active repository, plus `2.22` (RC1 on 13/10/2026), `milestone` and `devel`. The most conservative keep 2.17 and 2.18 (hashi_vault, amazon.aws).
* Python: derived from the series (e.g. community.general, units 2.21 → 3.9 / 3.12 / 3.14). For sanity/units, `--docker default` covers all the Python versions of the image: `v2.21-4` contains 3.9 to 3.14.
* `tests/sanity/ignore-2.X.txt` files: one per supported series, often up to `ignore-2.23.txt` (devel).

### 3.4 Changelog, lint, import, publication
* `changelogs/config.yaml` and mandatory fragments (`antsibull-changelog lint`, or the `ansible_validate_changelog` action, or the `skip-changelog` label).
* galaxy-importer: `python -m galaxy_importer.main --git-clone-path . --output-path /tmp` with `CHECK_REQUIRED_TAGS=True` (`ansible-content-actions/build_import.yaml`), or the nox session `build-import-check`.
* Publication: `release.yaml` (ansible-content-actions), publishing to Galaxy (`ANSIBLE_GALAXY_API_KEY`) and Automation Hub (`AH_TOKEN`).
* Docs: `ansible-community/github-docs-build` (`_shared-docs-build-pr.yml` / `-push.yml`), based on antsibull-docs.

## 5. Lessons for our context (airgapped, Jenkins + GitLab)

> **Note**: the survey describes upstream practice (series 2.19 → 2.22). The matrix chosen for AAP 2.6 is
> 2.16 + 2.18 (+ 2.20, see PROPOSITION §3). Points 1 and 2 led to an early nox prototype; the *principle*
> (all the logic in one place, the CI only orchestrates) is kept, but it is now carried by the bash CLI
> `aci` used by the central libraries, with no `noxfile.py` in the collections (PROPOSITION §1 and §20.2).

1. **The antsibull-nox pattern is the right one**: all the logic is in one place and the CI tool only calls it. This is what lets community.general run identically on GHA, on AZP and locally. For us, the same must hold for Jenkins and GitLab.
2. However, **antsibull-nox and tox-ansible download ansible-core from GitHub**, and the reusable GHA actions cannot be transposed. We keep the *principle* with our own tool that installs ansible-core from PyPI, hence through Nexus.
3. `--docker default` remains the reference method. The `quay.io/ansible/*` images only need to be provided **under their exact name**, and pip redirected inside the containers.
4. `--remote` integrations (Red Hat RHEL, FreeBSD, macOS, Windows VMs) must be replaced by distribution containers, or by internal VMs declared in a `--windows`/`--inventory` inventory.
